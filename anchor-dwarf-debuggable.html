Solana / sBPF toolchain note

Making Anchor programs debuggable

Stock Anchor builds ship zero debug information. The compiler emits perfectly good DWARF — two separate mechanisms throw it away before you ever see it. Here is what to change, and what it costs.

platform-tools v1.52 cargo-build-sbf 3.1.9 rustc 1.89.0-dev anchor-lang 0.32.1 anchor-cli 0.31.1 target sbpf-solana-solana
The short version

Set debug = 2 and strip = "none" in the release profile, then build with --debug --disable-remap-cwd. Neither change alone is sufficient.

Every claim on this page was measured against a built artifact, not inferred from documentation. Where something was not verified, it says so.

Why it disappears

Two independent strippers

A default anchor build produces a .so with nine sections and zero symbols. Nothing in it can support a source-level debugger.

1  Cargo strips at link time

Cargo injects -C strip=debuginfo whenever the profile has debug = 0. The release profile does, so the DWARF the compiler already produced is deleted during the final link. This is why setting debug = 2 without strip = "none" still gets you nothing.

2  cargo-build-sbf post-processes the deploy copy

The artifact written to target/deploy/ is run through strip.sh. Anything left is split out to <name>.debug with llvm-objcopy --only-keep-debug. The unstripped binary lives at target/sbpf-solana-solana/release/<name>.so.

Setting RUSTFLAGS yourself does not help: cargo-build-sbf explicitly discards your RUSTFLAGS and substitutes its own through CARGO_TARGET_<TRIPLE>_RUSTFLAGS.

The recipe

Two changes

STEP 1

Workspace Cargo.toml

[profile.release]
overflow-checks = true
lto = "fat"          # keep whatever you had
codegen-units = 1
debug = 2            # emit DWARF
strip = "none"       # stop cargo deleting it at link time

strip = "none" is not redundant. Without it, cargo's implicit -C strip=debuginfo removes everything debug = 2 just produced.

STEP 2

Build command

anchor build --no-idl -- --debug --disable-remap-cwd
--debug
Splits DWARF into target/deploy/<name>.debug. Without it you still get DWARF, but only inside target/sbpf-solana-solana/release/<name>.so.
--disable-remap-cwd
Preserves an absolute DW_AT_comp_dir so source lookup resolves. The default remaps it away and your debugger will not find the files.
--no-idl
Required — see the trap below.

Plain cargo-build-sbf --debug --disable-remap-cwd works identically and sidesteps the IDL problem entirely.

Traps

Three things that look right and are not

--debug on its own does nothing useful

The flag is documented as “Enable debug symbols”, which reads like it is the whole answer. It is not. Building with it alone adds 30,246 entries to .symtab and writes a 783 KB <name>.debug file — containing no .debug_* sections at all. Function names only. The profile change in Step 1 is what actually produces DWARF.

anchor build -- --debug fails after the program builds

Anchor forwards trailing arguments to cargo build-sbf — that part works, and you get a correct binary with all 22 compile units. It then reuses the same arguments for the cargo test invocation behind IDL generation, which rejects --debug and fails the build:

Error: Building IDL failed. Run `ANCHOR_LOG=true anchor idl build` to see the logs.

Use --no-idl and generate the IDL separately with anchor idl build.

Do not reach for opt-level = 0

The instinctive move to improve debuggability breaks sBPF. It overflows the 4 KB stack frame limit in six places, including inside Anchor's own generated dispatch:

Stack offset of 13152 exceeded max offset of 4096 by 9056 bytes  sha512_digest_block_u64
Stack offset of  9108 exceeded max offset of 4096 by 5012 bytes  sha256_digest_block_u32
Stack offset of  4568 exceeded max offset of 4096 by  472 bytes  vault::__private::__idl::__idl_dispatch

.text also grows 2.4× (0x23a98 → 0x55c60). A LiteSVM suite still passed on this build, but only because a toy program never calls the overflowing functions — a real program hits undefined behavior at runtime.

Design constraint

Debug info changes the bytecode

This is the part worth designing around. Enabling debug information does not merely annotate the binary — it perturbs codegen. Three clean-room builds of identical source produced three different .text sections:

stock                     0x23958   sha256 89e8635c…
debug=2 / strip=none      0x23a98   sha256 d9c55d64…
debug=2 + --debug         0x23a98   sha256 b93f563c…

Isolated with separate CARGO_TARGET_DIRs, so this is not the cwd-remap flag — it is debug information affecting inlining under LTO.

Consequence: debug info is only valid against the artifact it was built with, and that artifact's hash will not match a verifiable release build. Any tool consuming these should refuse to load a .debug against a mismatched .so rather than display subtly wrong line numbers.

What you get

DWARF quality

Good enough for real source-level debugging, including through Anchor's macro-generated code.

  • DWARF version 4 — sections are .debug_loc and .debug_ranges, not the v5 .debug_loclists / .debug_rnglists. Matters if you are writing a parser.
  • 22 compile units, 31,154 line-table rows, 7,062 subprograms (3,933 with concrete addresses; the rest inlined).
  • Location lists with register pieces: DW_OP_reg3, DW_OP_piece 0x8, DW_OP_reg4, DW_OP_piece 0x8.
  • DW_AT_frame_base (DW_OP_reg10) — the sBPF frame pointer.
  • Typed parameters resolve properly: solana_pubkey::Pubkey *, &[solana_account_info::AccountInfo].
  • Anchor handlers are attributed to real source. A #[program] function appears as vault::__private::__global::deposit with decl_file and decl_line pointing at your lib.rs, and macro-expansion closures as {closure#0}.
Before you build anything

Prior art and tooling gaps

solana-lldb already ships

Found at ~/.cache/solana/<ver>/platform-tools/llvm/bin/. It is an LLDB wrapper that preloads solana_lookup.py, registering type summaries for solana_program::pubkey::Pubkey and AccountInfo, alongside the standard Rust providers. Worth reading before duplicating it.

What is not in platform-tools

llvm-dwarfdump is absent — use a system copy. Present: lldb, llvm-objcopy, llvm-readelf, llvm-objdump, llvm-ar, clang, ld.lld.

Unverified — confirm before relying on it

How DWARF addresses (ELF virtual addresses, .text based at 0x120) map onto the runtime program counter in rbpf, where text is mapped at MM_PROGRAM_START and the pc is an instruction index. A translation layer is needed here; check it against the rbpf source rather than assuming text_vaddr + pc * 8.

Method

Findings were produced by building a real Anchor program under each configuration in isolated target directories, inspecting the resulting ELF and DWARF with llvm-readelf and llvm-dwarfdump, and executing each artifact through a LiteSVM test suite. Section sizes, symbol counts, DWARF entry counts and hashes on this page are measured values from those builds.

Numbers are from one small program; absolute counts will differ for yours. The relative comparisons and the behaviour of each flag are what transfer.
